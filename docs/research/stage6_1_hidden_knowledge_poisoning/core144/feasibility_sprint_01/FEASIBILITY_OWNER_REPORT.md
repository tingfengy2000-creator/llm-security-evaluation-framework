## 4. 新增机制为何没有成功

内部模块没有产生任何通过合同的证书，120条全部继续外证；88条在span/slot绑定处失败，32条通过原子合同但仍无证书。
所以E2逐ID与E1相同、E3与E4相同，内部模块没有检出或调用节约。
结构化核验118/120在span/slot绑定处被拒，另2条为模型自身未决；没有JSON语法失败，不能说模型不会输出JSON。
按校验器遍历顺序的首因分区可加总，但不代表独立因果贡献：

| 首因 | 条数 |
| --- | --- |
| PRESENT predicate值不在该atom的quote中 | 67 |
| PRESENT subject值不在quote中 | 18 |
| PRESENT scope_condition值不在quote中 | 9 |
| UID或逐字quote绑定失败 | 8 |
| PRESENT time_version值不在quote中 | 7 |
| PRESENT source_role值不在quote中 | 6 |
| PRESENT value_unit值不在quote中 | 3 |
| 原子合同通过，模型INSUFFICIENT | 2 |

110条首因是槽值不在对应原文片段内。当前输出不满足逐字合同；规范化/抽象槽值与逐字锚定冲突是合理解释，但字面失败本身不证明事实判断对错。
**本轮实现的输出合同可执行性是明确瓶颈。** 不能据此说中文S2/S3不可识别、结构化核验必然无效，或尚未获得有效输入的关系检查器已经有用。

封存后的RAW_VERDICT_DIAGNOSTIC显示：结构化原始CONTRADICT39条，其中Poison38、HN1；38个Poison判断全部被合同转为未决。
E1原始CONTRADICT40条，其中Poison38、HN2，最终为Poison37、HN1。这些只是错误归因，不是修复成绩；没有放宽parser、忽略无效引用或重打主分。
与旧L0不同，本轮六槽实现的失败明显集中在输出绑定，不能照搬旧L0“主要不是parser”的结论。
E1有10条引用失败、1条输出截断，另2条为无输出错误的模型自身未决，全部保留在120分母。
