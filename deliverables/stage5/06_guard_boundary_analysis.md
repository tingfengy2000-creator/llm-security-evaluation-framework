# Guard 能力边界

## 本阶段目标

通过六类攻击观察 rule-based GuardEngine 的覆盖面、绕过面和成本，而不是只展示成功拦截案例。

## 为什么这样设计

输入正则擅长明显覆盖语句；输出正则擅长已知危险字符串。角色混淆、上下文注入、数据外泄和工具意图往往需要语义分类、策略上下文和权限模型。

后续增强方向：

- 分类器：提高语义变体识别能力；
- LLM-as-judge：补充开放式风险判断，但需校准和防注入；
- 策略引擎：把用户、资源、动作和环境约束显式化；
- 上下文隔离：区分系统指令、用户输入和不可信检索内容；
- 工具权限：参数校验、最小权限、人工确认和沙箱。

## 和 Stage 4.1 的关系

Stage 4.1 证明 output guard 能拦截已知危险字符串；Stage 5 专门加入规则未覆盖类别，验证 baseline 的边界。

## 当前结论边界

工具样本只检测文本中的调用意图。框架没有连接、执行或模拟真实工具副作用。

最新离线 mock run 中 output-only 的 Output Block Rate 为 0%。原因是 Stage 4.1 的历史输出规则只覆盖已知仇恨字符串、脚本载荷和显式提示泄露，而 Stage 5 使用了新的合成标记。这个结果正好展示 rule-based baseline 对未知模式的覆盖缺口。

## 面试时怎么讲

“rule-based baseline 的价值是低延迟、可解释、可审计；缺点是覆盖依赖已知模式，所以我用 failure taxonomy 暴露绕过，而不是把它包装成完整方案。”

## 不能夸大的地方

Full Guard 只是输入规则和输出规则的组合，不是生产级纵深防御。
